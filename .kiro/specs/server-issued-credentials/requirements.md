# 요구사항 문서

## 소개

현재 채팅 애플리케이션의 회원가입 방식을 변경한다. 기존에는 사용자가 직접 아이디와 비밀번호를 선택하여 가입하는 방식이었으나, 보안이 허술한 사이트에서 사용자가 다른 사이트의 자격증명을 재사용하는 위험을 방지하기 위해, 서버가 아이디와 비밀번호를 랜덤으로 생성하여 발급하는 방식으로 전환한다. 사용자는 회원가입 시 표시 이름(displayName)과 이메일을 입력하며, 서버가 생성한 자격증명은 가입 완료 시 화면에 표시되고 이메일로도 발송된다. 또한 사용자가 자격증명을 분실했을 때 이메일을 통해 재발급받을 수 있는 흐름을 추가한다. 게스트로 이용 중인 사용자가 회원으로 전환할 수 있는 기능도 추가하며, 전환 시 기존 게스트 데이터(메시지, 참여 기록)는 새 회원 계정으로 이전된다. 이메일 발송은 AWS SES를 사용한다.

## 용어 정의

- **인증_서비스**: 회원가입, 로그인, 토큰 검증, 자격증명 재발급을 담당하는 서버 측 서비스 (`AuthService`)
- **회원가입_API**: 회원가입 요청을 처리하는 서버 엔드포인트 (`POST /api/auth/register`)
- **자격증명_생성기**: 서버에서 랜덤 아이디와 비밀번호를 생성하는 모듈
- **회원가입_페이지**: 사용자가 표시 이름과 이메일을 입력하고 회원가입을 요청하는 프론트엔드 화면 (`RegisterPage`)
- **자격증명_표시_화면**: 서버가 발급한 아이디와 비밀번호를 사용자에게 한 번 보여주는 프론트엔드 화면
- **로그인_페이지**: 사용자가 발급받은 아이디와 비밀번호로 로그인하는 프론트엔드 화면 (`LoginPage`)
- **자격증명_재발급_API**: 이메일 확인 후 새로운 비밀번호를 발급하여 이메일로 발송하는 서버 엔드포인트 (`POST /api/auth/reissue`)
- **자격증명_재발급_페이지**: 사용자가 이메일을 입력하여 자격증명 재발급을 요청하는 프론트엔드 화면
- **이메일_서비스**: AWS SES를 사용하여 이메일을 발송하는 서버 측 서비스
- **회원전환_API**: 게스트 사용자를 회원으로 전환하는 서버 엔드포인트 (`POST /api/auth/convert`)

## 요구사항

### 요구사항 1: 서버 측 랜덤 아이디 생성

**사용자 스토리:** 개발자로서, 서버가 고유한 랜덤 아이디를 생성하기를 원한다. 이를 통해 사용자가 다른 사이트에서 사용하는 아이디를 재사용하는 것을 방지할 수 있다.

#### 인수 조건

1. WHEN 회원가입 요청이 수신되면, THE 자격증명_생성기 SHALL "user-" 접두사와 4자리 랜덤 숫자로 구성된 고유한 아이디를 생성한다 (예: "user-3847")
2. THE 자격증명_생성기 SHALL 생성된 아이디가 기존 사용자 아이디와 중복되지 않도록 보장한다

### 요구사항 2: 서버 측 랜덤 비밀번호 생성

**사용자 스토리:** 개발자로서, 서버가 강력한 랜덤 비밀번호를 생성하기를 원한다. 이를 통해 사용자가 다른 사이트에서 사용하는 비밀번호를 재사용하는 것을 방지할 수 있다.

#### 인수 조건

1. WHEN 회원가입 요청이 수신되면, THE 자격증명_생성기 SHALL 8자의 영문 소문자와 숫자 조합으로 구성된 랜덤 비밀번호를 생성한다 (예: "ak3m92fx")
2. THE 인증_서비스 SHALL 생성된 비밀번호를 bcrypt로 해싱하여 데이터베이스에 저장한다
3. THE 인증_서비스 SHALL 평문 비밀번호를 데이터베이스에 저장하지 않고 회원가입 응답에만 포함한다

### 요구사항 3: 회원가입 API 변경

**사용자 스토리:** 사용자로서, 표시 이름만 입력하여 회원가입하기를 원한다. 이를 통해 아이디와 비밀번호를 직접 선택할 필요가 없어진다.

#### 인수 조건

1. WHEN 유효한 표시 이름과 이메일이 포함된 회원가입 요청이 수신되면, THE 회원가입_API SHALL 서버가 생성한 아이디, 비밀번호(평문), JWT 토큰, 사용자 정보를 응답으로 반환한다
2. WHEN 표시 이름이 비어있거나 누락된 회원가입 요청이 수신되면, THE 회원가입_API SHALL HTTP 400 상태 코드와 "표시 이름을 입력해주세요" 오류 메시지를 반환한다
3. WHEN 이메일이 비어있거나 누락된 회원가입 요청이 수신되면, THE 회원가입_API SHALL HTTP 400 상태 코드와 "이메일을 입력해주세요" 오류 메시지를 반환한다
4. WHEN 이미 등록된 이메일로 회원가입 요청이 수신되면, THE 회원가입_API SHALL HTTP 409 상태 코드와 "이미 사용 중인 이메일입니다" 오류 메시지를 반환한다
5. THE 회원가입_API SHALL 요청 본문에서 username과 password 필드를 더 이상 요구하지 않는다
6. THE 인증_서비스 SHALL 회원가입 응답에 생성된 아이디(generatedUsername)와 생성된 비밀번호(generatedPassword) 필드를 포함한다
7. WHEN 회원가입이 성공하면, THE 이메일_서비스 SHALL 사용자의 이메일로 발급된 아이디와 비밀번호를 발송한다

### 요구사항 4: 회원가입 페이지 변경

**사용자 스토리:** 사용자로서, 회원가입 시 표시 이름만 입력하는 간소화된 폼을 사용하기를 원한다. 이를 통해 가입 과정이 단순해진다.

#### 인수 조건

1. THE 회원가입_페이지 SHALL 표시 이름 입력 필드와 이메일 입력 필드, 회원가입 버튼을 표시한다
2. THE 회원가입_페이지 SHALL 아이디 입력 필드, 비밀번호 입력 필드, 비밀번호 확인 입력 필드를 제거한다
3. WHEN 회원가입이 성공하면, THE 회원가입_페이지 SHALL 자격증명_표시_화면으로 전환한다

### 요구사항 5: 자격증명 표시 화면

**사용자 스토리:** 사용자로서, 서버가 발급한 아이디와 비밀번호를 확인하기를 원한다. 이를 통해 발급받은 자격증명을 안전하게 보관할 수 있다.

#### 인수 조건

1. WHEN 회원가입이 완료되면, THE 자격증명_표시_화면 SHALL 서버가 생성한 아이디와 비밀번호를 화면에 표시한다
2. THE 자격증명_표시_화면 SHALL "이 정보는 다시 표시되지 않습니다. 안전한 곳에 보관해주세요."라는 경고 메시지를 표시한다
3. THE 자격증명_표시_화면 SHALL 아이디와 비밀번호를 각각 클립보드에 복사할 수 있는 복사 버튼을 제공한다
4. THE 자격증명_표시_화면 SHALL "확인했습니다" 버튼을 제공하고, WHEN 해당 버튼이 클릭되면 채팅방 목록 페이지로 이동한다

### 요구사항 6: 로그인 흐름 유지

**사용자 스토리:** 사용자로서, 발급받은 아이디와 비밀번호로 기존과 동일하게 로그인하기를 원한다. 이를 통해 로그인 방식에 혼란이 없다.

#### 인수 조건

1. THE 로그인_페이지 SHALL 기존의 아이디 입력 필드와 비밀번호 입력 필드를 유지한다
2. THE 인증_서비스 SHALL 기존 로그인 로직(아이디/비밀번호 검증, JWT 발급)을 변경 없이 유지한다
3. THE 로그인_페이지 SHALL 게스트 로그인 기능을 변경 없이 유지한다

### 요구사항 7: 자격증명 재발급

**사용자 스토리:** 사용자로서, 자격증명을 분실했을 때 재발급받기를 원한다. 이를 통해 서버가 발급한 자격증명을 잊어버려도 계정에 다시 접근할 수 있다.

#### 인수 조건

1. WHEN 유효한 이메일이 포함된 재발급 요청이 수신되면, THE 자격증명_재발급_API SHALL 해당 이메일로 등록된 사용자를 조회한다
2. WHEN 일치하는 사용자가 존재하면, THE 자격증명_재발급_API SHALL 새로운 랜덤 비밀번호를 생성하고, 해싱하여 저장한 뒤, 새 아이디와 비밀번호를 이메일로 발송한다
3. IF 이메일과 일치하는 사용자가 없으면, THEN THE 자격증명_재발급_API SHALL HTTP 404 상태 코드와 "일치하는 계정을 찾을 수 없습니다" 오류 메시지를 반환한다
4. THE 로그인_페이지 SHALL "자격증명을 잊으셨나요?" 링크를 제공하여 자격증명_재발급_페이지로 이동할 수 있도록 한다
5. THE 자격증명_재발급_페이지 SHALL 이메일 입력 필드를 제공한다
6. WHEN 재발급이 성공하면, THE 자격증명_재발급_페이지 SHALL "입력하신 이메일로 새 자격증명을 발송했습니다" 안내 메시지를 표시한다

### 요구사항 8: 기존 사용자 호환성

**사용자 스토리:** 기존 사용자로서, 이전에 직접 설정한 아이디와 비밀번호로 계속 로그인하기를 원한다. 이를 통해 기존 계정이 무효화되지 않는다.

#### 인수 조건

1. THE 인증_서비스 SHALL 기존 사용자 계정의 아이디와 비밀번호를 변경하지 않고 유지한다
2. THE 인증_서비스 SHALL 기존 사용자가 이전에 설정한 자격증명으로 로그인할 수 있도록 보장한다

### 요구사항 9: 게스트에서 회원으로 전환

**사용자 스토리:** 게스트 사용자로서, 회원으로 전환하여 다른 브라우저나 기기에서도 같은 계정으로 접속하기를 원한다. 이를 통해 게스트의 제한(현재 브라우저에서만 유효)을 벗어날 수 있다.

#### 인수 조건

1. WHEN 게스트 사용자가 회원전환을 요청하면, THE 회원전환_API SHALL 게스트의 UUID, 표시 이름, 이메일을 받아 새 회원 계정을 생성한다
2. THE 회원전환_API SHALL 서버가 생성한 아이디, 비밀번호(평문), JWT 토큰, 사용자 정보를 응답으로 반환한다
3. WHEN 회원전환이 성공하면, THE 회원전환_API SHALL 게스트 UUID로 된 메시지(messages 테이블의 user_id)를 새 회원 ID로 업데이트한다
4. WHEN 회원전환이 성공하면, THE 회원전환_API SHALL 게스트 UUID로 된 참여 기록(participants 테이블의 user_id)을 새 회원 ID로 업데이트한다
5. WHEN 회원전환이 성공하면, THE 이메일_서비스 SHALL 사용자의 이메일로 발급된 아이디와 비밀번호를 발송한다
6. THE 앱_헤더 SHALL 게스트 상태일 때 "회원전환" 버튼을 표시한다
7. WHEN "회원전환" 버튼이 클릭되면, THE 앱 SHALL 표시 이름과 이메일 입력 폼을 표시한다
8. WHEN 회원전환이 성공하면, THE 앱 SHALL 자격증명_표시_화면을 표시하고 클라이언트의 게스트 데이터(localStorage)를 삭제한다


## 향후 개선 사항

- **이메일 인증 코드**: 현재는 이메일 형식 검증만 수행하며, 실제 이메일 존재 여부는 확인하지 않는다. 향후 회원가입 시 이메일 인증 코드를 발송하여 실제 수신 가능한 이메일인지 확인하는 단계를 추가해야 한다.
- **계정 삭제**: 사용자가 직접 자신의 계정을 삭제할 수 있는 기능을 추가해야 한다. 계정 삭제 시 관련 데이터(메시지, 참여 기록 등) 처리 정책도 함께 정의해야 한다.
